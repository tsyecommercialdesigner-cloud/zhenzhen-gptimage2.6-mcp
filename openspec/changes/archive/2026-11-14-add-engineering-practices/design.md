# Design

## Context

见 [proposal](proposal.md)。当前项目使用 OpenSpec `spec-driven`，已批准的技术选型记载于 [原设计](../2026-11-09-add-image-generation-mcp/design.md)。本次将用户逐项接受的工程习惯整理为长期规范，不更改产品实现。

## Goals / Non-Goals

**Goals:** 在工程主规范中维护可审查的长期要求；将架构决策与已存在的测试、配置和验收事实明确区分。

**Non-Goals:** 不安装或变更 SDK、依赖、工作流或仓库设置；不创建或提前决定尚在讨论的手册撰写规范；不修改 AGENTS.md 或 CLAUDE.md。

## Decisions

### ADR-001：沿用现有技术架构并保留演进记录

- 状态：已接受；本条为既有决定的整理，不重写历史。
- 背景：项目已按用户决定采用 Python 3.12.14、uv、FastMCP、SQLite、httpx 和本地 stdio；旧通用指南建议官方 SDK，但不能覆盖本项目决定。
- 决策：保持现有架构；后续关键架构变更在相应 OpenSpec `design.md` 内记录背景、选项、决策、影响、验证和替代关系。
- 备选：将通用 SDK 固定为跨项目唯一选型；因不符合现有授权与项目选择而不采用。
- 影响与验证：旧设计仍为原始依据；本变更只确认工程规范，不声称进行 SDK 兼容迁移或真实验收。

### ADR-002：长期规范与变更材料分工

- 状态：已接受。
- 决策：`openspec/specs/engineering-practices/spec.md` 保存长期工程要求；变更 `proposal.md`、`design.md`、`tasks.md` 分别记录范围、设计/ADR 和任务状态。旧工程指南仅作为参考，不复制无关技术栈和场景。
- 备选：将所有规则放在根目录 CONVENTIONS.md 或单个归档 ADR；前者重复维护，后者不利于发现长期要求。

### ADR-003：真实验收证据与临时资源分开

- 状态：已接受。
- 决策：真实验收原件及脱敏账本保留在 Git 忽略的 `.cache/`；结论文档化并纳入版本控制。测试缓存和其他临时产物按归属分类清理，不能误删真实验收证据。
- 备选：删除全部 `.cache/` 或将全部原件提交 Git；分别会丢失证据或扩大私有数据暴露。

### ADR-004：历史增量与后续 Git 规则的关系

- 状态：已接受。历史增量保留当时的 Git 与合并验证条款，作为本变更的原始记录。
- 后续演进：现行 `engineering-practices` 主规范已经包含本变更的其他要求；Git 与合并验证要求经后续变更细化，并新增分支职责、单人审查和分阶段 CI/CD 条款。
- 归档处理：以现行主规范为准，归档时跳过历史增量的重复同步，避免以旧条款覆盖后续决定；首次 Host 联调配置与发布版验收环境要求已在主规范保留。

## Risks / Trade-offs

- [规范不等于已部署] → 文档区分期望要求与当前 CI、Host、发布及供应商的实际验证。
- [本机证据不可随 Git 获取] → 版本控制的结论记录证据范围与本地位置，不暗示其他成员可访问原件。

## Migration Plan

创建并核对工程主规范，验证 OpenSpec 和引用；已有代码、数据及用户配置不变。回滚文档变更应保留已有业务规范和验收记录。
