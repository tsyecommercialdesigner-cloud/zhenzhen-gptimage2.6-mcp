# engineering-practices Specification

## Purpose

为本项目维护可复核的工程习惯，贯通 OpenSpec、架构决策、分层验证、权限与副作用、版本控制、持续集成和交付，同时区分长期要求与实际运行状态。

## Requirements

### Requirement: 规范与变更追溯
项目 SHALL 使用用户确认的需求和 OpenSpec 主规范定义预期行为；以变更 proposal、design 和 tasks 分别记录范围、决策与任务状态，相关实现、测试和文档随变更协调更新。源码与证据反映实际状态，发现差异须报告，不以修改预期掩盖缺陷。

#### Scenario: 实现与规范不一致
- **WHEN** 检查发现当前实现与已确认规范不一致
- **THEN** 记录差异及证据，再决定修复或经确认调整规范

#### Scenario: 小型修正
- **WHEN** 变更影响范围较小
- **THEN** 按实际影响选择适当流程，不机械要求所有变更具有相同材料规模

### Requirement: 架构决策与兼容性
项目 SHALL 在相关变更 design.md 中记录关键架构决策的背景、备选、决定、影响、验证和替代关系；分别记录运行时、SDK、协议、传输和 Host 的兼容与验证范围，不将本项目选型强加于其他项目。

#### Scenario: 考虑替换关键组件
- **WHEN** 提议替换框架或存储等关键组件
- **THEN** 记录替代关系、迁移影响和验证依据，未经决策不自动迁移

### Requirement: 依赖与检查可复现
项目 SHALL 维护运行时声明、依赖声明和锁文件一致；提供实际存在且失败返回非零的适用检查入口，CI 与本地使用相应入口，日常启动复用已安装环境，不自动安装或升级依赖。

#### Scenario: 必需检查缺失或失败
- **WHEN** 适用的必需检查缺失或失败
- **THEN** 明确报告并停止通过结论，不用空脚本或跳过步骤掩盖

### Requirement: 分层验证与证据
项目 SHALL 区分单元与契约、实际 SDK 协议、Host 和真实供应商验证，记录通过、失败、不适用或未验证；证据关联必要版本、环境、预期、结果与范围，并脱敏。

#### Scenario: 离线替身通过
- **WHEN** 上游替身测试成功
- **THEN** 仅报告替身验证范围，不宣称真实供应商或 Host 验收通过

### Requirement: 测试资源及证据保留
项目 SHALL 使用隔离测试资源，结束时先保留必要证据，再停止和分类清理本次创建的缓存、临时环境及不需保留产物；保留用户数据、源码和 fixtures。真实验收原件及脱敏账本保留在 Git 忽略的 `.cache/`，验收结论纳入版本控制。

#### Scenario: 清理测试产物
- **WHEN** 测试结束或中断
- **THEN** 不删除需保留的真实验收原件和账本，仅清理归属已确认的临时资源；清理失败报告位置和原因

### Requirement: MCP 契约与信任边界
项目 SHALL 明确能力用途、输入、输出、错误、权限与副作用，服务端落实状态和数据约束；Skill 按需组织任务，Host 负责发现及权限交互，不将 Skill 或工具描述当成授权、沙箱或服务端校验。

#### Scenario: 工具执行失败
- **WHEN** 业务工具执行失败
- **THEN** 按适用协议返回可识别的失败，不伪装为成功

### Requirement: 副作用与恢复
项目 SHALL 明确收费或写入操作的授权、幂等、超时、取消、重试和恢复边界；结果未知时先查询可用状态，不自动重复提交或跨供应商切换。文件、网络和外部内容按实际权限及资源边界处理。

#### Scenario: 生成结果未知
- **WHEN** 付费请求可能已送达而结果未知
- **THEN** 保留证据并查询可用状态，不自动发起第二次生成

### Requirement: 结果来源与响应预算
项目 SHALL 按适用能力筛选、分页并限制响应规模，保留必要来源、时间、状态、任务标识和完整结果定位；截断、缺失及部分失败须明确报告，长说明按需引用。

#### Scenario: 查询结果超过单页范围
- **WHEN** 结果超出单页或响应预算
- **THEN** 明确范围并提供适用的续取方式，不静默丢弃关键结果

### Requirement: Git 与合并验证
项目 SHALL 按用途跟踪源码、测试、安全 fixtures、锁、规范与共享工作流，排除秘密及本地生成状态；变更使用可评审分支和 PR，适用检查通过后按授权合并，并根据实际合入差异确定复验范围，不强制每次合并重跑完整 CI。

#### Scenario: 调整忽略规则
- **WHEN** 修改 Git 忽略规则
- **THEN** 验证应忽略和应跟踪的正反例，不以宽泛扩展名规则代替用途判断

### Requirement: 分支职责与单人审查
项目 SHALL 使用 `main`、`dev` 和 `feature/*` 分工：`main` 保持可发布，`dev` 集成开发变更，`feature/*` 从 `dev` 创建并经 PR 合回 `dev`，不得直接合入 `main`；发布时通过 `dev → main` PR 汇总已选变更。单人维护时，审查由维护者结合 Agent 和适用 CI 结果完成，不强制其他人批准；Agent 与自动检查的角色和实际结果须如实记录。

#### Scenario: 功能完成后集成
- **WHEN** 一个 feature 通过适用检查并合入 `dev`
- **THEN** 可继续积累其他功能，不因此自动发起发布 PR 或发布

#### Scenario: 单人维护者审查 PR
- **WHEN** 维护者准备合并 PR
- **THEN** 由维护者结合 Agent 审查及适用检查判断变更，无须其他人的独立 Review；适用检查缺失或失败仍须处理并如实报告

### Requirement: 分阶段 CI 与发布验收
项目 SHALL 根据变更影响选择检查，并区分日常集成、发布候选、合并确认和正式发布；同一阶段避免重复的 PR 与 push 全量检查，正式 CD 只通过一个受控入口在实际发布时执行，不因普通合并自动重复发布。

#### Scenario: feature 合入 dev
- **WHEN** `feature/* → dev` PR 提交检查
- **THEN** 按实际影响执行适用的格式、类型、相关测试与安全检查；纯文档变更执行适用文档检查，合入 `dev` 不重复运行同一套 push CI 或触发发布

#### Scenario: 发布候选验收
- **WHEN** 创建 `dev → main` 发布 PR
- **THEN** 对累计变更执行完整发布验收并生成适用候选产物，记录被验证的源码、依赖、构建配置、检查结果及产物标识

#### Scenario: main 合并结果复验
- **WHEN** 发布 PR 合入 `main`
- **THEN** 将实际合入内容与已验收候选比较；相关输入一致时仅运行必要的快速检查，有差异时重跑受影响检查，缓存命中本身不能证明验证通过

#### Scenario: 实际发布
- **WHEN** 维护者决定正式发布
- **THEN** 通过唯一受控发布入口使用与已验证输入一致的产物，记录标签、提交和结果，并按实际结果更新 README 与 MANUAL；不因日常合并触发 CD

#### Scenario: 文档仓库的适用检查
- **WHEN** 变更属于规范文档仓库
- **THEN** 以适用的链接、格式、示例解析及秘密扫描为主；涉及安装命令或跨平台行为时增加对应验证

### Requirement: CI 工作流安全
项目 SHALL 对工作流采取最小权限，隔离不可信 PR 和生产秘密；第三方 Actions 固定经核对的完整提交 SHA，输入与秘密不得拼入可执行脚本、日志或缓存。失败停止发布，门禁配置以实际验证状态报告。

#### Scenario: 外部 PR 检查
- **WHEN** 检查外部或分叉 PR
- **THEN** 不向其不可信代码或产物提供生产秘密及发布写权限

### Requirement: 版本发布与恢复
项目 SHALL 将发布版本关联标签、完整提交 SHA、适用 CI 与安装验收；升级保留用户配置和数据，回滚考虑依赖、协议和数据库兼容，不将切换代码等同于恢复数据。

#### Scenario: 数据库迁移后回滚
- **WHEN** 旧版本不兼容当前数据库
- **THEN** 按验证过的备份恢复方案处理并保留必要数据，不强行用旧版本重写
